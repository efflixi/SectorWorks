CROSS-PLATFORM DISK IMAGE WORKSPACE
DETAILED STARTER TECHNICAL SPECIFICATION
Version 0.3
Date: October 12, 2026
Status: Feasibility / Initial Architecture


1. DOCUMENT PURPOSE

This document defines the initial technical architecture, platform targets, functional scope, safety model, and implementation direction for a cross-platform desktop application used to inspect, browse, extract, modify, rebuild, and validate disk and optical-media image files.

This is a starter specification. Exact product features, final supported formats, minimum operating-system versions, packaging methods, and detailed user-interface requirements will be revised as the application concept matures.


2. PRODUCT SUMMARY

The application will provide a unified workspace for opening and working with common disk and optical-media image formats entirely within the application.

The application will not rely on mounting an image as a host operating-system drive, volume, or mount point. Instead, it will interpret the image through its own storage subsystem and expose partitions, filesystems, directories, files, tracks, and metadata through its own interface.

The intended user experience is similar to opening an archive in an archive manager. A user should be able to open an image, browse its contents, extract files, queue modifications, and save the changes according to the capabilities of the image format and contained filesystem.

Some formats may support direct modification. Other formats, particularly optical-media formats such as ISO or BIN/CUE, may require the application to rebuild and save a replacement image rather than modify the source image in place.

Primary product goal:

- Provide consistent functionality across Windows, macOS, and Linux.
- Platform implementations do not need to be identical.
- Platform-specific methods may be used where necessary, provided the user-facing capabilities and results remain reasonably consistent.

Format support must be capability-based rather than extension-based. A recognized file extension does not guarantee that every internal variation can be safely modified or rebuilt.


6.2.1 RETRO-COMPUTING FLOPPY PRIORITIES

360K and 720K PC floppy images are important product requirements for retro-computing workflows, not incidental compatibility:
- 360K: 368,640 bytes for a conventional raw image; typically 40 cylinders, two heads, nine 512-byte sectors per track.
- 720K: 737,280 bytes for a conventional raw image; typically 80 cylinders, two heads, nine 512-byte sectors per track.

Capacity describes raw sector data, not a separate filesystem or a guarantee that every image of that length is supported. Detection must validate the contained layout rather than infer a filesystem solely from size or extension.

Retain the Phase 1 read-only 720K compatibility already demonstrated by the supplied Compaq diagnostic disk and synthetic legacy FAT12 fixtures. This includes a narrowly validated early-DOS BIOS parameter block (BPB) path without the conventional 0x55AA trailer; it is not blanket support for all historical variants.

Broader 360K/720K compatibility and its qualification belong to Phase 7 - Additional Formats and Filesystems. Work includes representative fixtures, early-DOS BPB variations, geometry/media-descriptor validation, legacy volume labels, safe handling of missing or inconsistent metadata, and independently checked browsing/extraction. Write/create/conversion and bootability or exact-layout preservation remain separate capabilities requiring their own tests and the applicable staged-write/commit safeguards. Track/sector-structured and flux captures require separate format evaluation; raw IMG support does not imply support for them.

6.6 EDITING CAPABILITY DELIVERY ROADMAP

Owner-approved roadmap clarification, October 15, 2026:

The current roadmap targets release 1.0. VMDK, VDI, QCOW2, DMG, ext2/ext3/ext4, exFAT, HFS+ and APFS target qualified read-only subsets for 1.0 where feasible. Modification, staged writing, Save As of modified images, direct commit, rebuild, creation and formatting for these additions are outside 1.0 requirements, not unassigned release-blocking writer gaps. No post-1.0 writer delivery date or milestone is promised.

Phase 7 still requires reader evaluation, legal fixtures and tests for exact supported variants/features. Detection-only is not browsing/extraction. Document concrete limitations and feasibility blockers for owner review; do not silently remove a reader requirement if infeasible or infer blanket read support from this goal. Core access uses internal parsers, never host mounting: native Windows/Linux/macOS mounting support does not determine application parser capability. Track platform limitations from executed evidence.

Apply the read-only cap compositionally: a read-only container keeps even FAT/NTFS read-only, and ext/exFAT/HFS+/APFS remain read-only inside otherwise writable raw/VHD/VHDX. This boundary does not reduce the core raw/VHD/VHDX FAT/ordinary-NTFS, optical or retro writing milestones below.

Read support does not automatically provide editing, Save As, direct commit, or rebuild. The checklist must assign explicit delivery and qualification tasks for each required container -> partition layout -> filesystem -> feature-subset combination. A single working combination proves the initial feasibility milestone, not completion of the broader editing roadmap.

Delivery assignments:
- Phase 2 retains its verified initial conventional unpartitioned raw FAT12/FAT16/FAT32 DOS 8.3 editing and Save As subset.
- Phase 2B, a separate milestone before Phase 3, expands staged editing and validated Save As to raw, fixed/dynamic VHD and fixed/dynamic VHDX with filesystem-only, valid primary MBR and valid GPT layouts containing conventional FAT12/FAT16/FAT32 or ordinary supported NTFS, where structurally valid. Each container variant, partition arrangement, supported sector-size combination and filesystem requires its own qualification row.
- Phase 2B also delivers a declared FAT long-filename/mixed-case/Unicode writing subset and portable modification of existing ordinary NTFS volumes. NTFS creation/formatting remains a separate capability; the known dependency Windows SID formatting failure must not be treated as proof that all NTFS modification is impossible.
- Phase 3 explicitly qualifies safe direct commit for the Phase 2B rows, including the initial Phase 2 subset. Generic transaction infrastructure or one successful combination is insufficient.
- Phase 4 integrates ISO 9660, Joliet and supported Rock Ridge subsets with shared staged editing and validated rebuild. It also delivers a declared UDF read/edit/rebuild subset and separately qualified ISO/UDF bridge rebuild, rather than leaving UDF detection as the only scheduled capability.
- Phase 6 integrates qualified BIN/CUE data and mixed-mode layouts with shared staged editing and validated new-output-set rebuilding, including safe multi-file publication.
- Phase 7 item 7.10 separately qualifies conventional 360K/720K FAT12 staged editing, Save As and safe direct commit; wider legacy variants remain capability-gated. Creation and conversion require separate qualification.

For disk containers, validated copy-and-apply Save As and qualified direct commit are normally the applicable save modes; rebuilding every format is not mandatory. Format-aware reconstruction is required when the layout cannot safely absorb changes, particularly optical media. Record inapplicable save modes with reasons rather than conflating them with missing writers.

Each required row must remain incomplete or blocked until verified. If safe implementation is not achievable, obtain an explicit owner-approved scope decision; a named follow-up milestone is required only for work still required by the roadmap. Intentional 1.0 read-only additions need no invented future writer milestone; evaluation alone does not fulfill required reader or writer delivery tasks. Unsupported variants must remain safely read-only with reasons. Differencing parents, VHDX active-log replay, filesystem repair and partition creation/movement/resizing are not implicitly added by the editing expansion.

Qualification must cover all advertised operations, staged browse/preview/hex/search/extraction, history/discard, capacity and naming rules, source integrity, new-output publication, independent reopen, and container/partition/filesystem allocation and metadata validation in addition to tree/content hashes. Preserve untouched volumes, opaque regions and supported metadata, or refuse the write. Direct commit additionally requires per-stack locking, backup, journal, interruption and recovery evidence. Bootability and exact-layout preservation remain independently tested capabilities, not automatic consequences of successful file editing.

This is a documentation/roadmap correction, not permission to implement a phase. Phase 2B and every later phase require separate authorization and the normal verification/user-review gate. Historical Phase 2 completion remains limited to its recorded envelope. See checklist.txt for the authoritative task status and per-phase exit criteria.


7. STORAGE ARCHITECTURE

Storage logic must be separated into independent layers.

Conceptual Data Path:

Image File
  -> Container Handler
  -> Virtual Block Device
  -> Partition Table Handler
  -> Partition / Logical Block Device
  -> Filesystem Handler
  -> Files and Directories
  -> Workspace and UI

For optical-media images, the data path may instead be:

Image File(s)
  -> Optical Container Handler
  -> Disc Sessions and Tracks
  -> Data Track
  -> ISO 9660 / UDF Filesystem
  -> Files and Directories
  -> Workspace and UI

Each layer must use interfaces that prevent upper levels from depending on one specific file format or filesystem.


7.1 BLOCK DEVICE ABSTRACTION

The block-device layer should provide:
- Random-access reads.
- Controlled random-access writes where supported.
- Logical size.
- Logical and physical sector-size information where known.
- Flush operation.
- Read-only state.
- Bounds validation.
- Optional sparse or differencing behavior.
- Optional change-overlay support.

Container handlers should expose one or more block devices without requiring filesystem handlers to understand the underlying container format.


7.2 CONTAINER HANDLERS

Each image-container handler should be responsible for:
- Format detection.
- Header and metadata parsing.
- Exposing virtual block devices or optical tracks.
- Reading data ranges.
- Writing data ranges when supported.
- Handling dynamic, sparse, or differencing structures.
- Validating container consistency.
- Reporting save capabilities.

Examples:
- Raw handler
- VHD handler
- VHDX handler
- ISO handler
- BIN/CUE handler


7.3 PARTITION HANDLERS

Partition handlers should be responsible for:
- Detecting MBR or GPT structures.
- Enumerating partitions.
- Exposing each partition as a bounded block-device view.
- Reporting partition type and metadata.
- Detecting overlaps and invalid offsets.
- Preserving unknown partition metadata when possible.


7.4 FILESYSTEM HANDLERS

Filesystem handlers should be responsible for:
- Filesystem detection.
- Directory enumeration.
- File reading.
- Metadata access.
- File and directory modification where supported.
- Allocation and deallocation.
- Metadata consistency.
- Flush and validation operations.
- Reporting supported capabilities.

Filesystem handlers must not directly depend on operating-system filesystem drivers.

10. SAVE AND COMMIT MODES


10.1 DIRECT COMMIT

Direct commit may be available when both the container and contained filesystem safely support modification.

Possible examples:
- Raw IMG containing a supported FAT filesystem.
- VHD containing a writable supported filesystem.
- VHDX containing a writable supported filesystem.

Direct commit must still use validation, flushing, locking, and recovery safeguards.


10.2 REBUILD REQUIRED

Rebuild mode will be used when safe or practical in-place modification is unavailable.

Likely examples:
- ISO images.
- BIN/CUE images with modified data tracks.
- Structured or compressed containers that cannot absorb arbitrary changes safely.
- Images requiring layout regeneration.

The application should clearly indicate:

This image cannot be safely modified in place. Saving will create a rebuilt image.

Rebuild output should normally be written to a temporary or new file, validated, and only then used to replace the original if the user requested replacement.


10.3 READ-ONLY MODE

A workspace must be read-only when:
- The image or source file is not writable.
- The format is recognized but no writer is available.
- The filesystem is supported only for reading.
- Required parent images are missing.
- The image is encrypted and cannot be unlocked.
- Structural corruption makes writing unsafe.
- Exact reconstruction cannot be guaranteed.
- Unsupported metadata would be destroyed by modification.

Read-only mode should still permit browsing, previewing, extraction, metadata inspection, and conversion/export where possible.


11. ISO HANDLING

ISO images will generally be treated as rebuild-oriented media rather than normally writable filesystems.

The application should support:
- ISO structure detection.
- ISO 9660 browsing.
- Joliet names where present.
- Rock Ridge support if provided by the selected storage implementation.
- UDF support where available.
- File extraction.
- Queued additions, replacements, deletions, and renames.
- Rebuilding to a new ISO.

Special preservation concerns include:
- El Torito boot catalog.
- BIOS boot images.
- UEFI boot images.
- Hybrid MBR/GPT layouts.
- Joliet metadata.
- Rock Ridge metadata.
- UDF structures.
- Volume identifiers.
- File ordering and alignment.

The application must not claim that bootability or exact layout will be preserved unless the rebuild engine has explicitly confirmed that capability.


12. BIN/CUE HANDLING

BIN/CUE support will be treated as an advanced feature.

The handler may need to represent:
- Multiple sessions.
- Multiple tracks.
- Data tracks.
- Audio tracks.
- Mixed-mode discs.
- Sector modes and sizes.
- Pregaps and postgaps.
- Track indexes.
- Raw sector data.
- Optional subchannel-related information.

A data-only BIN/CUE image may expose its filesystem similarly to an ISO. A mixed-mode image must also expose tracks that do not contain an ordinary filesystem.

CD audio tracks should be playable directly from the image when selected. Playback must not require extraction of the track to a separate file first. Audio playback is a read-only operation and should remain available even when the image workspace itself is read-only.

Integrated CD audio playback should provide:
- Play.
- Pause.
- Stop.
- Seek within the selected track.
- Previous and next audio track navigation.
- Volume control.
- Elapsed time and total track duration.

The optical-media subsystem should expose CD-DA audio as a stream suitable for the application audio layer while preserving the original sector representation. Playback implementation may differ by platform, but playback capability and user-facing behavior should remain consistent.

Possible workspace representation:

Disc Image
  Track 01 - Data
    Filesystem contents
  Track 02 - Audio [Playable]
  Track 03 - Audio [Playable]

Modification may require rebuilding a new BIN/CUE set. The application must report whether it can preserve:
- Track order.
- Exact indexes.
- Gaps.
- Sector mode.
- Audio data.
- Subchannel information.
- Bootability.

If exact preservation is not possible, modification should be disabled or require an explicit informed conversion/rebuild operation.


13. SAFETY AND DATA INTEGRITY

Data integrity is a primary requirement.

The application must assume that image files may contain valuable, bootable, or irreplaceable data.

Required safeguards:
- Open source images read-only until modification is requested.
- Obtain an exclusive or advisory lock before committing where supported.
- Detect external source-file changes during an open session.
- Prevent concurrent internal writers to the same image.
- Validate all offsets, lengths, sector calculations, and allocations.
- Refuse writes outside valid image boundaries.
- Flush writes before reporting completion.
- Validate rebuilt or modified output before replacing the original.
- Preserve the original image until successful completion.
- Use temporary files on the same filesystem when atomic replacement is needed.
- Provide clear failure and recovery information.

Recommended commit sequence:

1. Verify source identity and modification time.
2. Acquire write lock.
3. Validate pending changes.
4. Verify free space and temporary-storage requirements.
5. Create backup, snapshot, overlay, or temporary output as required.
6. Apply changes.
7. Flush all writes.
8. Reopen the result independently.
9. Validate container, partition, and filesystem structures.
10. Atomically replace the original only when requested and supported.
11. Retain recovery information until completion is confirmed.

A fast direct-write mode without backup may be considered later, but it should require explicit user selection and warnings.


14. LARGE-FILE AND PERFORMANCE REQUIREMENTS

Image files may range from kilobytes to multiple terabytes.

The application must:
- Avoid loading complete images into memory.
- Use streaming and random-access I/O.
- Use bounded buffers.
- Support asynchronous operations.
- Keep the UI responsive during long operations.
- Report progress, throughput, and estimated completion when practical.
- Permit cancellation when cancellation will not corrupt output.
- Use memory mapping only behind an abstraction and only when beneficial.
- Handle sparse files without unnecessarily expanding them.
- Avoid unnecessary full-image copies when safe alternatives exist.

The Raspberry Pi 5 will serve as a useful ARM64 performance baseline for the Linux desktop build. The UI and common browsing operations should remain responsive on this class of hardware.

20. SECURITY CONSIDERATIONS

Image files are untrusted input.

The application must defend against:
- Invalid lengths and offsets.
- Integer overflow.
- Recursive directory cycles.
- Excessive nesting.
- Extremely large metadata counts.
- Crafted filenames.
- Path traversal during extraction.
- Symbolic-link extraction attacks.
- Decompression or allocation bombs.
- Corrupt partition tables.
- Malformed filesystem structures.
- Malicious image metadata.

Extraction must never write outside the user-selected destination.

Preview handlers must be sandboxed or limited where practical. The application should not automatically execute content from an image.

Storage parsing should use checked arithmetic and strict bounds validation.


21. LOGGING AND RECOVERY

The application should maintain structured logs for:
- Image detection.
- Workspace opening.
- Capability decisions.
- Validation warnings.
- Pending operations.
- Commit/rebuild stages.
- Errors and recovery actions.

Logs must avoid storing file contents unless explicitly enabled for diagnostics.

For interrupted operations, the application should detect:
- Incomplete temporary images.
- Pending recovery journals.
- Backups created by the application.
- Source images changed during the previous session.

The user should receive clear recovery choices without requiring knowledge of internal storage structures.


22. OUT-OF-SCOPE FOR INITIAL DEVELOPMENT

The following should not be assumed part of the first release:
- Host operating-system drive mounting.
- Kernel drivers.
- General-purpose filesystem repair.
- Partition movement and resizing.
- Full forensic analysis.
- Data recovery from severely damaged filesystems.
- Guaranteed bit-identical BIN/CUE rebuilding.
- Guaranteed preservation of every bootable ISO variation.
- Encrypted-volume cracking or bypass.
- Virtual-machine execution.
- Network block-device hosting.
- 32-bit operating systems or processors.

These may be evaluated separately after the core workspace is stable.


23. PROPOSED DEVELOPMENT PHASES

Phase 1 - Read-Only Explorer
- Establish Avalonia application shell.
- Implement block-device abstractions.
- Open raw IMG, VHD, VHDX, and ISO.
- Detect MBR and GPT.
- Browse FAT, NTFS, and ISO 9660 where supported.
- Extract files and directories.
- Display image, partition, and filesystem properties.

Phase 2 - Staged File Modification
- Add pending-change model.
- Add file replacement, addition, deletion, and rename operations.
- Add change review.
- Implement save-as-new-image workflows.
- Add output validation.

Phase 2B - Existing Disk-Format Editing Expansion
- Qualify shared staged editing and validated Save As for raw, fixed/dynamic VHD and fixed/dynamic VHDX with filesystem-only, primary MBR and GPT FAT/ordinary-NTFS layouts.
- Add a qualified FAT long-filename/mixed-case/Unicode writer subset.
- Qualify portable existing-volume NTFS modification separately from formatting.
- Preserve and validate container/partition/filesystem metadata, allocation and unchanged content for every required row.
- Stop for verification and user review before Phase 3.

Phase 3 - Safe Direct Commit
- Qualify direct writes for each required Phase 2B container/layout/filesystem row, not merely one combination.
- Add locking, backup, journaling, validation, and recovery.
- Add external-change detection.
- Require per-stack failure/recovery evidence or explicit owner-approved scope decisions with named follow-up milestones.

Phase 4 - ISO Rebuild
- Add controlled ISO rebuild.
- Preserve supported naming extensions and metadata.
- Add bootability capability detection and warnings.
- Integrate ISO 9660/Joliet/Rock Ridge staged editing and qualify each advertised naming/metadata subset.
- Deliver a declared UDF read/staged-edit/rebuild subset and consistent ISO/UDF bridge rebuild; unsafe/unavailable delivery stays blocked pending owner decision.

Phase 5 - Linux and ARM64 Hardening
- Validate all core functions on Linux x86-64 and ARM64.
- Optimize Raspberry Pi 5 performance.
- Verify X11 and Wayland behavior.

Phase 6 - BIN/CUE and Optical Expansion
- Parse CUE sheets and track layouts.
- Browse supported data tracks.
- Represent audio and mixed-mode tracks.
- Add direct playback of CD audio tracks from supported images.
- Add rebuild workflows only where preservation requirements are understood.
- Integrate qualified data-track staged editing and validate safe publication/recovery of complete BIN/CUE output sets.

Phase 7 - Additional Formats and Filesystems
- Evaluate VMDK, VDI, QCOW2, DMG, ext filesystems, exFAT, HFS+, and APFS.
- Expand and qualify retro-floppy compatibility, prioritizing 360K and 720K PC images while retaining the existing read-only 720K subset.
- Add formats incrementally according to testability and user value.
- Explicitly qualify conventional 360K/720K staged editing, Save As and safe direct commit; track creation/conversion separately.
- Qualify feasible read-only subsets of VMDK/VDI/QCOW2/DMG/ext/exFAT/HFS+/APFS for 1.0; document concrete reader blockers for owner review without promising later writers.


24. FEASIBILITY PROTOTYPE

Before committing to full application development, create a focused proof of concept that demonstrates:
- One Avalonia UI codebase running on Windows, Linux, and macOS.
- x86-64 and ARM64 builds.
- Opening a raw IMG, VHD/VHDX, and ISO.
- Detecting partition tables.
- Browsing at least FAT and NTFS images.
- Extracting files.
- Queuing one replacement operation.
- Saving to a new image.
- Reopening and validating the output.
- Running the ARM64 Linux build on a Raspberry Pi 5.

The feasibility prototype should prioritize correctness and architecture validation rather than polished UI or broad format coverage.
