SECTORWORKS DEVELOPMENT CHECKLIST
Workflow Revision: 0.3

Purpose:
This checklist converts the SectorWorks technical phases into an agent-executable implementation plan. It is intentionally more concrete than the technical specification.

WORKFLOW AUTHORITY
- The command "Start Phase N" authorizes autonomous work through THAT PHASE ONLY.
- Agents must read rules.txt, this checklist, and relevant specifications before beginning.
- Agents may proceed through individual tasks in the authorized phase without asking for approval for each task.
- Agents must NEVER begin a later phase without explicit user approval.
- A later-phase dependency discovered during current work must be noted under the affected item and reported to the user.
- At the end of every phase, the agent must perform verification, update this checklist truthfully, request user review, and STOP.
- Phase 2B is a separate owner-approved roadmap milestone between Phase 2 and Phase 3. It requires explicit implementation authorization; documentation approval is not authorization to start it.

STATUS KEY
[ ] Not started / incomplete
[x] Completed and verified
[-] Intentionally not applicable or explicitly deferred
[!] Blocked, uncertain, requires user decision, or blocked by a later-phase dependency

GLOBAL RULES
    NOTE: Continuous requirements, re-evaluated for every phase. Per-phase
    evidence is recorded in verification gates, not permanent exemptions.

[ ] Never require host-OS mounting for core image access.
[ ] Do not assume images fit in memory; prefer streaming/random access and bounded buffers.
[ ] Keep long operations off the UI thread.

[ ] Add tests with new storage functionality in the phase that introduces it.

CAPABILITY DELIVERY COVERAGE
    NOTE: Owner approved this roadmap correction on 2026-10-15, including
    a separate Phase 2B before Phase 3. No implementation authorized by it.
    Phase 2's verified initial subset remains complete within its recorded
    envelope; its "at least one" exit is not the product-wide editing target.
[ ] Maintain named container -> partition layout -> filesystem -> feature-subset rows for planned and delivered capabilities.
[ ] Track staged operations, Save As, direct commit, rebuild, validation, bootability and exact-layout preservation independently for each row.
[ ] Assign every required incomplete capability to a phase/item; generic infrastructure or library APIs do not complete any row.
[ ] Keep required rows incomplete/blocked until verified, or obtain explicit owner approval for a documented scope change; require a named follow-up milestone only for capabilities still required by the roadmap.
[ ] Do not substitute a single successful stack for the required coverage of a phase.
    NOTE: Disk images normally use copy-and-apply Save As or qualified direct
    commit; optical layouts normally require reconstruction. Rebuild is not
    automatically required for every readable format. Record why a save mode
    is inapplicable; an unavailable required writer is a gap/blocker, not an exemption.
    Owner decision, 2026-10-15: this roadmap targets 1.0. VMDK, VDI, QCOW2,
    DMG, ext2/ext3/ext4, exFAT, HFS+ and APFS target qualified read-only
    subsets where feasible. Their modification/staging, modified Save As,
    direct commit, rebuild, creation and formatting are outside 1.0 requirements,
    not release-blocking writer gaps. No post-1.0 delivery date is promised.
    Phase 7 must still evaluate readers and publish exact tested subsets or
    concrete blockers; detection-only is not browsing/extraction, and infeasible
    readers require owner review rather than silent removal. Apply the cap
    compositionally: a read-only container caps FAT/NTFS too; a read-only
    filesystem stays read-only inside raw/VHD/VHDX. Internal parsers, not the
    host OS's native mount support, determine access on every platform.
