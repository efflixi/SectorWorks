CROSS-PLATFORM DISK IMAGE WORKSPACE
DETAILED STARTER TECHNICAL SPECIFICATION
Version 0.3
Date: October 12, 2026
Status: Feasibility / Initial Architecture


1. DOCUMENT PURPOSE

This document defines the initial technical architecture, platform targets, functional scope, safety model, and implementation direction for a cross-platform desktop application used to inspect, browse, extract, modify, rebuild, and validate disk and optical-media image files.

This is a starter specification. Exact product features, final supported formats, minimum operating-system versions, packaging methods, and detailed user-interface requirements will be revised as the application concept matures.


2. PRODUCT SUMMARY

The application will provide a unified workspace for opening and working with common disk and optical-media image formats entirely within the application.

The application will not rely on mounting an image as a host operating-system drive, volume, or mount point. Instead, it will interpret the image through its own storage subsystem and expose partitions, filesystems, directories, files, tracks, and metadata through its own interface.

The intended user experience is similar to opening an archive in an archive manager. A user should be able to open an image, browse its contents, extract files, queue modifications, and save the changes according to the capabilities of the image format and contained filesystem.

Some formats may support direct modification. Other formats, particularly optical-media formats such as ISO or BIN/CUE, may require the application to rebuild and save a replacement image rather than modify the source image in place.

Primary product goal:

- Provide consistent functionality across Windows and Linux.
- Platform implementations do not need to be identical.
- Platform-specific methods may be used where necessary, provided the user-facing capabilities and results remain reasonably consistent.

6. FUNCTIONAL SCOPE


6.1 CORE IMAGE WORKSPACE

The application will open each image as an internal workspace, normally represented by a tab or document window.

A workspace should expose:
- Image path and basic metadata.
- Detected container format.
- Image size and logical sector information.
- Partition table, if present.
- Partitions and unallocated regions.
- Filesystems detected on each partition or directly in the image.
- Directory and file contents.
- Optical-disc sessions and tracks where applicable.
- Selectable CD audio tracks with integrated playback where applicable.
- Current access and save capabilities.
- Pending changes.
- Validation results and warnings.

Suggested workspace states:
- Opening
- Ready / Read-only
- Ready / Writable
- Ready / Rebuild required
- Modified
- Committing
- Rebuilding
- Validating
- Failed
- Closed

The term mount may be used informally in internal discussion, but user-facing terminology should prefer:
- Open Image
- Image Workspace
- Close Image
- Commit Changes
- Rebuild Image
- Save Image As
- Discard Changes

This avoids implying that the image is attached to the host operating system.

6.2.1 RETRO-COMPUTING FLOPPY PRIORITIES

360K and 720K PC floppy images are important product requirements for retro-computing workflows, not incidental compatibility:
- 360K: 368,640 bytes for a conventional raw image; typically 40 cylinders, two heads, nine 512-byte sectors per track.
- 720K: 737,280 bytes for a conventional raw image; typically 80 cylinders, two heads, nine 512-byte sectors per track.

Capacity describes raw sector data, not a separate filesystem or a guarantee that every image of that length is supported. Detection must validate the contained layout rather than infer a filesystem solely from size or extension.

Retain the Phase 1 read-only 720K compatibility already demonstrated by the supplied Compaq diagnostic disk and synthetic legacy FAT12 fixtures. This includes a narrowly validated early-DOS BIOS parameter block (BPB) path without the conventional 0x55AA trailer; it is not blanket support for all historical variants.

Broader 360K/720K compatibility and its qualification belong to Phase 6 - Additional Formats and Filesystems. Work includes representative fixtures, early-DOS BPB variations, geometry/media-descriptor validation, legacy volume labels, safe handling of missing or inconsistent metadata, and independently checked browsing/extraction. Write/create/conversion and bootability or exact-layout preservation remain separate capabilities requiring their own tests and the applicable staged-write/commit safeguards. Track/sector-structured and flux captures require separate format evaluation; raw IMG support does not imply support for them.

7. STORAGE ARCHITECTURE

Storage logic must be separated into independent layers.

Conceptual Data Path:

Image File
  -> Container Handler
  -> Virtual Block Device
  -> Partition Table Handler
  -> Partition / Logical Block Device
  -> Filesystem Handler
  -> Files and Directories
  -> Workspace and UI

For optical-media images, the data path may instead be:

Image File(s)
  -> Optical Container Handler
  -> Disc Sessions and Tracks
  -> Data Track
  -> ISO 9660 / UDF Filesystem
  -> Files and Directories
  -> Workspace and UI

Each layer must use interfaces that prevent upper levels from depending on one specific file format or filesystem.


7.1 BLOCK DEVICE ABSTRACTION

The block-device layer should provide:
- Random-access reads.
- Controlled random-access writes where supported.
- Logical size.
- Logical and physical sector-size information where known.
- Flush operation.
- Read-only state.
- Bounds validation.
- Optional sparse or differencing behavior.
- Optional change-overlay support.

Container handlers should expose one or more block devices without requiring filesystem handlers to understand the underlying container format.


7.2 CONTAINER HANDLERS

Each image-container handler should be responsible for:
- Format detection.
- Header and metadata parsing.
- Exposing virtual block devices or optical tracks.
- Reading data ranges.
- Writing data ranges when supported.
- Handling dynamic, sparse, or differencing structures.
- Validating container consistency.
- Reporting save capabilities.

Examples:
- Raw handler
- VHD handler
- VHDX handler
- ISO handler
- BIN/CUE handler


7.3 PARTITION HANDLERS

Partition handlers should be responsible for:
- Detecting MBR or GPT structures.
- Enumerating partitions.
- Exposing each partition as a bounded block-device view.
- Reporting partition type and metadata.
- Detecting overlaps and invalid offsets.
- Preserving unknown partition metadata when possible.


7.4 FILESYSTEM HANDLERS

Filesystem handlers should be responsible for:
- Filesystem detection.
- Directory enumeration.
- File reading.
- Metadata access.
- File and directory modification where supported.
- Allocation and deallocation.
- Metadata consistency.
- Flush and validation operations.
- Reporting supported capabilities.

Filesystem handlers must not directly depend on operating-system filesystem drivers.

Original Image
  -> Readable Base Layer

  -> Workspace View
  -> Validation
  -> Commit In Place or Rebuild

Pending operations should include:
- Add
- Replace
- Delete
- Rename
- Create directory
- Metadata change

The change manager should support:
- Ordered command execution.
- Undo and redo where practical.
- Conflict detection.
- Capacity checks.
- Duplicate-name detection.
- Case-sensitivity rules.
- Estimated output size.
- Change review before commit.
- Discarding all pending changes.

The user should be able to select:
- Commit Changes
- Save as New Image
- Rebuild Image
- Discard Changes


10. SAVE AND COMMIT MODES


10.1 DIRECT COMMIT

Direct commit may be available when both the container and contained filesystem safely support modification.

Possible examples:
- Raw IMG containing a supported FAT filesystem.
- VHD containing a writable supported filesystem.
- VHDX containing a writable supported filesystem.

Direct commit must still use validation, flushing, locking, and recovery safeguards.


10.2 REBUILD REQUIRED

Rebuild mode will be used when safe or practical in-place modification is unavailable.

Likely examples:
- ISO images.
- BIN/CUE images with modified data tracks.
- Structured or compressed containers that cannot absorb arbitrary changes safely.
- Images requiring layout regeneration.

The application should clearly indicate:

This image cannot be safely modified in place. Saving will create a rebuilt image.

Rebuild output should normally be written to a temporary or new file, validated, and only then used to replace the original if the user requested replacement.


10.3 READ-ONLY MODE

A workspace must be read-only when:
- The image or source file is not writable.
- The format is recognized but no writer is available.
- The filesystem is supported only for reading.
- Required parent images are missing.
- The image is encrypted and cannot be unlocked.
- Structural corruption makes writing unsafe.
- Exact reconstruction cannot be guaranteed.
- Unsupported metadata would be destroyed by modification.

Read-only mode should still permit browsing, previewing, extraction, metadata inspection, and conversion/export where possible.


11. ISO HANDLING

ISO images will generally be treated as rebuild-oriented media rather than normally writable filesystems.

The application should support:
- ISO structure detection.
- ISO 9660 browsing.
- Joliet names where present.
- Rock Ridge support if provided by the selected storage implementation.
- UDF support where available.
- File extraction.
- Queued additions, replacements, deletions, and renames.
- Rebuilding to a new ISO.

Special preservation concerns include:
- El Torito boot catalog.
- BIOS boot images.
- UEFI boot images.
- Hybrid MBR/GPT layouts.
- Joliet metadata.
- Rock Ridge metadata.
- UDF structures.
- Volume identifiers.
- File ordering and alignment.

The application must not claim that bootability or exact layout will be preserved unless the rebuild engine has explicitly confirmed that capability.


12. BIN/CUE HANDLING

BIN/CUE support will be treated as an advanced feature.

The handler may need to represent:
- Multiple sessions.
- Multiple tracks.
- Data tracks.
- Audio tracks.
- Mixed-mode discs.
- Sector modes and sizes.
- Pregaps and postgaps.
- Track indexes.
- Raw sector data.
- Optional subchannel-related information.

A data-only BIN/CUE image may expose its filesystem similarly to an ISO. A mixed-mode image must also expose tracks that do not contain an ordinary filesystem.

CD audio tracks should be playable directly from the image when selected. Playback must not require extraction of the track to a separate file first. Audio playback is a read-only operation and should remain available even when the image workspace itself is read-only.

Integrated CD audio playback should provide:
- Play.
- Pause.
- Stop.
- Seek within the selected track.
- Previous and next audio track navigation.
- Volume control.
- Elapsed time and total track duration.

The optical-media subsystem should expose CD-DA audio as a stream suitable for the application audio layer while preserving the original sector representation. Playback implementation may differ by platform, but playback capability and user-facing behavior should remain consistent.

13. SAFETY AND DATA INTEGRITY

Data integrity is a primary requirement.

The application must assume that image files may contain valuable, bootable, or irreplaceable data.

Required safeguards:
- Open source images read-only until modification is requested.
- Obtain an exclusive or advisory lock before committing where supported.
- Detect external source-file changes during an open session.
- Prevent concurrent internal writers to the same image.
- Validate all offsets, lengths, sector calculations, and allocations.
- Refuse writes outside valid image boundaries.
- Flush writes before reporting completion.
- Validate rebuilt or modified output before replacing the original.
- Preserve the original image until successful completion.
- Use temporary files on the same filesystem when atomic replacement is needed.
- Provide clear failure and recovery information.

Recommended commit sequence:

1. Verify source identity and modification time.
2. Acquire write lock.
3. Validate pending changes.
4. Verify free space and temporary-storage requirements.
5. Create backup, snapshot, overlay, or temporary output as required.
6. Apply changes.
7. Flush all writes.
8. Reopen the result independently.
9. Validate container, partition, and filesystem structures.
10. Atomically replace the original only when requested and supported.
11. Retain recovery information until completion is confirmed.

A fast direct-write mode without backup may be considered later, but it should require explicit user selection and warnings.


14. LARGE-FILE AND PERFORMANCE REQUIREMENTS

Image files may range from kilobytes to multiple terabytes.

The application must:
- Avoid loading complete images into memory.
- Use streaming and random-access I/O.
- Use bounded buffers.
- Support asynchronous operations.
- Keep the UI responsive during long operations.
- Report progress, throughput, and estimated completion when practical.
- Permit cancellation when cancellation will not corrupt output.
- Use memory mapping only behind an abstraction and only when beneficial.
- Handle sparse files without unnecessarily expanding them.
- Avoid unnecessary full-image copies when safe alternatives exist.

The Raspberry Pi 5 remains a useful ARM64 performance reference. Physical reference performance/GUI qualification is NOT VERIFIED — DEFERRED POST-1.0 BY OWNER to P1.ARM64.LINUX, not a 1.0 gate or a claim established by cross-building.

20. SECURITY CONSIDERATIONS

Image files are untrusted input.

The application must defend against:
- Invalid lengths and offsets.
- Integer overflow.
- Recursive directory cycles.
- Excessive nesting.
- Extremely large metadata counts.
- Crafted filenames.
- Path traversal during extraction.
- Symbolic-link extraction attacks.
- Decompression or allocation bombs.
- Corrupt partition tables.
- Malformed filesystem structures.
- Malicious image metadata.

Extraction must never write outside the user-selected destination.

Preview handlers must be sandboxed or limited where practical. The application should not automatically execute content from an image.

Storage parsing should use checked arithmetic and strict bounds validation.


21. LOGGING AND RECOVERY

The application should maintain structured logs for:
- Image detection.
- Workspace opening.
- Capability decisions.
- Validation warnings.
- Pending operations.
- Commit/rebuild stages.
- Errors and recovery actions.

Logs must avoid storing file contents unless explicitly enabled for diagnostics.

For interrupted operations, the application should detect:
- Incomplete temporary images.
- Pending recovery journals.
- Backups created by the application.
- Source images changed during the previous session.

The user should receive clear recovery choices without requiring knowledge of internal storage structures.


22. OUT-OF-SCOPE FOR INITIAL DEVELOPMENT

The following should not be assumed part of the first release:
- Host operating-system drive mounting.
- Kernel drivers.
- General-purpose filesystem repair.
- Partition movement and resizing.
- Full forensic analysis.
- Data recovery from severely damaged filesystems.
- Guaranteed bit-identical BIN/CUE rebuilding.
- Guaranteed preservation of every bootable ISO variation.
- Encrypted-volume cracking or bypass.
- Virtual-machine execution.
- Network block-device hosting.
- 32-bit operating systems or processors.

These may be evaluated separately after the core workspace is stable.
